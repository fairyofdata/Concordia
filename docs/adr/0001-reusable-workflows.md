# 0001. CI를 재사용 워크플로 한 곳에 모으고, 큰 판 태그로 부른다

- 상태: 채택 (2026-11-24)

## 맥락
- 파이썬 테스트가 있는 저장소 다섯 곳의 CI가 거의 같은 꼴(checkout → setup-python → pip install → pytest)인데, 저장소마다 따로 적혀 있어 action 판과 파이썬 판이 제각각이었다.
- 공개 저장소에 들어가면 안 되는 것(로컬 상태 파일, 개인 경로)을 사람이 diff를 보다가 잡는 일이 있었다.

## 결정
1. 공용 워크플로는 이 저장소의 `workflow_call` 워크플로로 둔다. 부르는 쪽은 `uses: fairyofdata/Concordia/.github/workflows/<이름>.yml@v1`.
2. 이 저장소는 공개다. 공개 저장소는 공개 저장소의 재사용 워크플로만 부를 수 있다(GitHub 규칙).
3. 판은 큰 판 태그(`v1`)로 낸다. 호환되는 변경은 태그를 옮기고, 입력 이름이나 기본 동작이 바뀌면 `v2`를 낸다.
4. `python-tests.yml`은 설치·테스트 명령을 입력으로 받는다. 저장소마다 다른 부분은 명령에만 둔다.
5. `hygiene.yml`은 형식 검사만 한다: 추적되면 안 되는 파일 이름, 홈 디렉터리 절대 경로 꼴, 내부 번호 꼴(경고). 파일이 무엇에 관한 것인지는 판단하지 않는다 — 그런 판단은 낱말 목록으로 하면 반드시 놓치므로 여기서 하지 않는다.
6. 검사 스크립트는 `concordia-ref`(기본 `v1`)에서 받아 온다. 워크플로와 스크립트의 판이 어긋나지 않게 `uses:`의 태그와 같게 둔다. 이 저장소 자신은 `github.sha`로 부른다.

## 버린 대안
- 저장소마다 워크플로 복사: 지금 상태. 고칠 때마다 저장소를 다 돌아야 한다.
- 복합 action(`action.yml`): 단계 묶음은 되지만 판 행렬과 작업 단위 권한을 부르는 쪽이 다시 써야 한다.

## 결과
- 부르는 쪽 CI 파일은 열 줄 안팎이 된다.
- 대가: 이 저장소의 실수가 부르는 저장소 모두에 퍼진다. 자체 검사(`self-check.yml`: 자기 워크플로로 자기 테스트·위생 검사, actionlint)를 통과한 커밋에만 태그를 옮긴다.
